## 0. Read this first — CARLA 0.9.16 changes the answer

**Everything in sections 2 and 6 exists to work around a signal that 0.9.16 makes
directly readable.** We are on 0.9.15.2 (`git describe` on the source tree), which is
why the workarounds were necessary at all.

CARLA's changelog, under Latest Changes after 0.9.15:

> *Added API function `get_telemetry_data` to the vehicle actor.*

`carla::client::Vehicle` declares `TelemetryData GetTelemetryData() const`, returning
`rpc::VehicleTelemetryData`:

```cpp
struct VehicleTelemetryData {          struct WheelTelemetryData {
    float speed;                           float tire_friction;
    float steer;                           float lat_slip;
    float throttle;                        float long_slip;        // kappa
    float brake;                           float omega;            // WHEEL SPEED
    float engine_rpm;                      float tire_load;        // Fz  [N]
    int32_t gear;                          float normalized_tire_load;
    float drag;                            float torque;           // Trq_T2W
    std::vector<WheelTelemetryData> wheels;  float long_force;     // Fx
};                                         float lat_force;        // Fy
                                           float normalized_long_force;
                                           float normalized_lat_force;
                                       };
```

**`omega` and `torque`, per wheel.** Those are the two quantities this entire document
was written to reconstruct. The server-side builder runs **unconditionally** — it reads
`PxWheelQueryResult` plus the `UVehicleWheel` debug fields directly, with no dependence
on `show_debug_telemetry` or the HUD.

**It is reachable from Python**, verified at all three layers of the binding:

```cpp
// PythonAPI/carla/source/libcarla/Actor.cpp
.def("get_telemetry_data", CONST_CALL_WITHOUT_GIL(cc::Vehicle, GetTelemetryData))

// PythonAPI/carla/source/libcarla/Control.cpp
class_<cr::WheelTelemetryData>("WheelTelemetryData")
    .def_readwrite("omega",     &cr::WheelTelemetryData::omega)
    .def_readwrite("torque",    &cr::WheelTelemetryData::torque)
    .def_readwrite("long_slip", &cr::WheelTelemetryData::long_slip)
    .def_readwrite("tire_load", &cr::WheelTelemetryData::tire_load)

class_<cr::VehicleTelemetryData>("VehicleTelemetryData", no_init)
    .add_property("wheels", &GetWheelsTelemetry, &SetWheelsTelemetry)
```

so the bench-side call is simply:

```python
t = vehicle.get_telemetry_data()
for i, w in enumerate(t.wheels):
    w_cmd[i]   = w.omega        # rad/s, straight to the hub dyno
    Trq_T2W[i] = w.torque       # Nm
```

### What this retires

| Was | Now |
|---|---|
| §6.2 `vdot` inverse to reconstruct `sum Fx` | unnecessary — read `torque` per wheel |
| §4.1 drag area inferred from Blueprint defaults, unverified | unnecessary — `drag` is reported directly |
| §7 per-wheel **read** needs a fork | **false on 0.9.16** — telemetry is per-wheel |
| C-1, C-3, C-4, C-5 | resolved |

### What it does *not* change

**The write side is still lumped.** `get_telemetry_data` is read-only. Injecting `Taxl`
still goes through `apply_control`, which is one scalar throttle split by CARLA's
differential — so you can *measure* per wheel but only *command* a lumped torque. The
flattened-drivetrain work in §6.1 is still required, and is still verified.

Per-wheel **command** remains the one thing needing the `SimpleWheeled` fork (§7).

### Consequence for the recommendation

On 0.9.16 the loop closes exactly as it does with CarMaker, with no reconstruction:

```
Taxl_i  ->  pedal map (flattened drivetrain)  ->  CARLA
CARLA   ->  get_telemetry_data().wheels[i].omega   ->  w_cmd_i
                                  .wheels[i].torque ->  Trq_T2W_i
```

**Design B becomes the better option on 0.9.16**, and the §9 recommendation of Design A
holds only while we remain on 0.9.15. Upgrading is now the highest-value action in this
document.

## 1. The problem, and why it is not the CarMaker problem

The dyno loop needs one signal from the vehicle model:

```
I * dw/dt  =  Taxl  +  Trq_T2W
```

CarMaker supplies `Trq_T2W` directly, on the wire. **CARLA will not**, and no amount
of configuration changes that — so the two designs below differ in how they route
around it.

---

## 2. What CARLA 0.9.15 will and will not tell you

**This section describes 0.9.15 only — see §0, which 0.9.16 resolves.**

Measured by sweeping every public getter on `carla.Vehicle`:

| | |
|---|---|
| **Readable** | `get_velocity`, `get_angular_velocity`, `get_acceleration`, `get_transform`, `get_control`, `get_physics_control`, **`get_wheel_steer_angle`** |
| **Not readable** | wheel speed, longitudinal slip, tire force, normal load — *anything* per-wheel except the steer angle |

The data exists. UE4's `UVehicleWheel` carries `DebugLongSlip`, `DebugLatSlip`,
`DebugTireLoad`, `DebugWheelTorque`, `DebugLongForce`, `DebugLatForce` as plain
public fields, and CARLA already holds the pointer (`CarlaWheeledVehicle.cpp:309`).
`show_debug_telemetry` renders them to the HUD. **There is simply no RPC path.**

Consequence: `Trq_T2W` and `omega_i` are both unavailable. Every design below is a
way of living with that.

## 3. CARLA's backend, per physics substep

```
per wheel i:
  Fz_i        from the suspension raycast (spring + damper on jounce)
  vx_i, vy_i  contact-point velocity, from chassis v and Omega
  kappa_i   = ( omega_i*r - vx_i ) / |vx_i|
  alpha_i   = atan( vy_i / |vx_i| )
  (Fx_i, Fy_i, tau_i) = TireShader(kappa_i, alpha_i, Fz_i, mu, omega_i, r)
                        with tau_i = -Fx_i * r

wheel:    J_w * domega_i/dt  =  T_drive_i - T_brake_i - Fx_i*r
chassis:  m * dv/dt          =  sum_i(Fx_i + Fy_i + Fz_i) + m*g + F_drag + F_ext
          I * dOmega/dt      =  sum_i(r_i x F_i) + T_ext
```

Below 0.2 m/s with `omega_i == 0` and no throttle — or after 1 s at low speed — PhysX
replaces the tire force with a **sticky-tire velocity constraint**
(`PxVehicleUpdate.cpp:2166`). A constraint, not a force, so it absorbs any applied
force. This is why `add_force` cannot move a stationary car.

### Where each API acts

| API | Term |
|---|---|
| `apply_control(throttle)` | sets `T_drive_i`; also sets `isIntentionToAccelerate`, releasing sticky tires |
| `apply_control(brake)` | sets `T_brake_i` |
| `add_force(F)` | adds `F_ext` **at the centre of mass** |
| `set_target_velocity(v)` | **overwrites `v`**, once |
| `enable_constant_velocity(v)` | **overwrites `v`** every substep, in body frame |
| `apply_physics_control` | calls `RecreatePhysicsState()` — rebuilds the vehicle |

## 4. Constants recovered from source

Neither is exposed by the API; both were recovered by reading code and assets.

### 4.1 Chassis drag — the only chassis-level force

`UWheeledVehicleMovementComponent::UpdateDrag`:

```
Fres = 0.5 * AirDensity * Cd * (ChassisWidth * ChassisHeight) * v_fwd * |v_fwd|

AirDensity = 1.25 kg/m^3     hardcoded, not 1.225
direction  = along the NOSE  (-GlobalForwardVector), not along velocity
speed      = ForwardSpeed, signed
dead zone  = |ForwardSpeed| < 1 cm/s
```

Its `AddForce` is the **only** chassis-level force in the whole movement component.
Everything else — rolling resistance, engine braking, wheel damping — acts on the
*wheel* and reaches the body inside `sum Fx`.

`ChassisWidth` and `ChassisHeight` are `UPROPERTY(EditAnywhere)`, so they live in the
Blueprint asset, and CARLA never sets or reads them. They are **absent** from
`BP_TeslaM3.uasset`, `BP_Tesla_FLW.uasset` and `BaseVehiclePawn.uasset` — and UE4 only
serialises properties that differ from the class default. So CARLA leaves them at
UE4's defaults:

```
A = 1.80 m * 1.40 m = 2.52 m^2      the same for every CARLA vehicle
```

**Not yet verified in motion** — see §8.

### 4.2 Wheel inertia

```
UVehicleWheel::Mass = 20.0 kg            class default; absent from CARLA's wheel BPs
PWheelData.mMOI = 0.5 * mMass * mRadius^2      solid disc

=> J_w = 0.5 * 20.0 * r^2      = 1.369 kg m^2 for r = 0.37 m
```

**Verified to 1.1%** — see §8.

## 5. Design A — impose the speed

The dyno loop owns all longitudinal dynamics, including road load from the vehicle's
own measured A, B, C coefficients. CARLA is told the answer.

```
dyno + road-load model  ->  v(k)
                            v(k)  ->  enable_constant_velocity( (v,0,0) )      body frame
CARLA                   ->  pose, lateral, traffic, signals, sensors
                            w_cmd_i(k) = v(k) / r   -> evenly to all hub units
```

**Why it works.** The write rejects any external force completely; the residual is
exactly one integration step of that force and does not accumulate. Measured against a
known applied force equivalent to slopes from 0 to 20 degrees, the error tracked the
prediction `-a*dt` across a 10x range and reached only 0.069 m/s (0.46%) on a 20-degree
slope.

**The wheels keep up.** The write leaves `omega_i` untouched, so the tire re-syncs it:

```
tau = J_w * v / ( r^2 * Cs ),   Cs = long_stiff_value * g = 3000 * 9.81 = 29,430 N

  v = 10 m/s -> 3.4 ms      v = 20 -> 6.8 ms      v = 30 -> 10.2 ms
```

Against a 20-50 ms tick that is 3 to 15 time constants, so `omega_i` sits at `v/r` and
the mismatch never accumulates.

**What it costs.** Writing velocity along the nose imposes **zero sideslip** — measured
0.45 deg against 21 deg for a freely driven car in the same corner. The vehicle moves
exactly where it points. Yaw is still dynamic (it comes from the tire), so the path is
correct; what you lose is drift, oversteer and anything at the friction limit.

**Use `enable_constant_velocity`, not `set_target_velocity`.** Measured difference:
the former is **latched and in body frame** — called once, it held 15.00 m/s
indefinitely and stayed within 1.3 deg of the nose through a 130 deg turn. The latter is
a **one-shot world-frame** write: called once, the speed decayed immediately and drifted
16 deg off the nose. Both require physics enabled; with physics off the car moved 0.000 m
in 1.0 s.

## 6. Design B — inject the torque

CARLA's own tire, wheel and body physics run. The bench feeds torque in through the
pedals, and the wheel speed is recovered from the body's motion.

### 6.1 The drivetrain must be flattened first

Stock, `throttle -> wheel torque` is **not** a gain. `moi = 1.0` reflected through
`final_ratio = 9` is **81 kg m^2 at the wheel — 592 kg of equivalent mass**, plus clutch
slip. Measured: the implied effective mass varied **47%** across throttle and ran 2-3x
above prediction.

Neutralise it once, at setup (`apply_physics_control` is setup-time only, §3):

```
moi             -> 0.01          kills the reflected engine inertia
clutch_strength -> 1e4           no slip
final_ratio     -> 1.0
forward_gears   -> [ratio 1.0],  use_gear_autobox = False
torque_curve    -> flat at T0
damping rates   -> 0             no engine braking
```

**Measured after flattening:** effective mass spread **2.7%** across a 3.4x throttle
range, and within **1.1%** of `m + 4*J_w/r^2` predicted from source. So:

```
Taxl >= 0 :  throttle = Taxl / T0
Taxl <  0 :  brake    = |Taxl| / (n_wheels * max_brake_torque)
```

### 6.2 Recovering the wheel speed

Since only aero and gravity act on the chassis outside the tire:

```
sum Fx   =  m * dv/dt  +  Fres(v)  +  m*g*sin(theta)
Trq_T2W  =  -r * sum Fx
```

`dv/dt` by differencing `get_velocity` in synchronous mode — **not** `get_acceleration`,
which read 15.55 m/s^2 vertically on a stationary car and clearly carries suspension
transients.

From there, either integrate the wheel yourself using the verified `J_w`, or invert the
tire law algebraically for `kappa` and get `omega = v(1+kappa)/r`. The algebraic route
avoids a second integrator but needs `Fz_i`, which must be estimated.

## 7. The ceiling both designs share

**Both are lumped, single-axis.** Not by choice:

- **In:** `throttle` is one scalar. Torque reaches the wheels through CARLA's
  differential, which decides the split. Left and right cannot be commanded separately.
- **Out:** the `vdot` inverse yields `sum Fx` from body acceleration. Splitting it per
  wheel needs per-wheel `Fz` and slip, neither exposed.

So a per-wheel hub dyno gains nothing from Design B over Design A. Everything reachable
through the public API treats the vehicle as one axis.

**The only per-wheel path is a fork.** UE4 ships
`USimpleWheeledVehicleMovementComponent`, which wraps `PxVehicleNoDrive` — the source
comment reads *"a simple PxNoDrive which will give us suspension but no engine forces
which we leave to the user."* It exposes exactly what the bench wants:

```cpp
void SetDriveTorque(float DriveTorque, int32 WheelIndex);
void SetBrakeTorque(float BrakeTorque, int32 WheelIndex);
void SetSteerAngle (float SteerAngle,  int32 WheelIndex);
```

Per-wheel torque, no engine, suspension and tires intact. The engine class already
exists; what is missing is a CARLA vehicle class that uses it (CARLA already has the
pattern — `ACarlaWheeledVehicleNW` sits alongside the 4W one) and RPC bindings.

## 9. Recommendation

**Design A**, using `enable_constant_velocity`, for longitudinal work where the dyno
owns road load from real coastdown coefficients. CARLA's aero is a fixed 2.52 m^2 box
and its tire has no relaxation length, so putting CARLA's longitudinal physics in the
loop buys little when you have measured coefficients for the actual vehicle.

**Design B** is proven and stands ready if the argument changes — specifically if you
want CARLA's tire participating, or slip to be emergent rather than imposed.

**The fork** is the only answer if per-wheel torque and speed are genuine requirements.
That is a scope decision, not a technical one: the public API cannot do it.
